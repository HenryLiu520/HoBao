# 开发流程地图（可复用）

> 这份文档不属于「荷包」，它属于**你**。
> 以后开任何新项目，先翻这份，走一遍这 6 步。

---

## 0. 为什么要有流程

新手最常见的干法是「走一步看一步」：先写个界面，再加个功能，再看情况接数据库。

**问题不在慢，在返工成本是指数增长的：**

| 发现问题的时机 | 修复代价 |
|---|---|
| 需求阶段 | 改一行文字 |
| 数据建模阶段 | 改一个字段 |
| 写完界面之后 | 改界面 + 改逻辑 |
| 数据库接好、有真实数据之后 | 改数据模型 + **迁移已有数据** + 改所有读它的地方 |

所以流程的价值不是「规范」「专业感」，而是：**把返工锁在小范围内。**

**三条贯穿全程的原则：**

1. **每个阶段都是下一个阶段的输入。** 跳过一步，代价会在下游被放大。
2. **验收标准必须客观。** 「做完了」不能是感觉，得是能演示出来的状态。
3. **最不确定的先做。** 风险前置，早暴露早调整。

## 阶段 0 · 需求 —— 把「我想做 X」变成功能清单

### 做法

**① 写「用户故事（User Story）」，不要写功能名。**

统一模板：

> **作为**〈谁〉，**我想**〈做什么〉，**这样我就能**〈得到什么〉。

对比一下：

- ❌ `多币种功能` ← 这不是需求，这是"我要一个东西"
- ✅ `作为在香港上学的内地学生，我想用人民币/日元记账并且自动折算成港币，这样我就不用自己心算汇率`

用户故事的价值在于：**它逼你说出"谁"和"为什么"**。说不出"这样我就能…"的功能，通常可以直接砍掉。

**② 每个故事问三个问题：**

| 问题 | 它决定了 |
|---|---|
| 谁会用？多久用一次？ | 高频动作必须做得极快，低频的可以丑 |
| 没有它，app 还能用吗？ | 不能 = 必须有（Must） |
| 做它的前提是什么？ | 直接决定开发顺序 |

**③ 砍。** 用 MoSCoW 分类：

- **Must**：没有它 app 不成立
- **Should**：很重要，但可以晚一个版本
- **Could**：锦上添花
- **Won't**：明确不做（写下来也很重要，防止以后反复纠结）

### 产出

一页功能清单。

### 验收标准

每个条目都能一句话说清「谁 / 什么时候 / 用来干什么」，并且标注了 Must / Should / Could。

## 阶段 1 · 数据建模 —— 把功能翻译成「要存什么」

### 为什么它是最关键的一步

> **改界面是改一天的事，改数据模型是改全项目的事。**

这是唯一「改错代价最大」的阶段。所以它值得你花最长时间想，而且必须**在写界面之前**想。

### 做法

**① 从句子里挑名词 → 候选实体（Entity）**

逐条读你的用户故事，把名词圈出来：

- 「记一笔**账单**」 → 实体：账单
- 「按**分类**看」 → 实体：分类
- 「用不同**货币**记」 → 实体：货币（或只是账单上的一个字段，见下）

每个名词问一句：**它是一个独立的东西，还是只是别的实体身上的一个属性？**

- 「分类」是独立实体，因为分类有自己的属性（名字、颜色），而且会被多条账单共用。
- 「货币」多数情况下只是一个字符串字段 + 一个汇率数字，**不需要**独立成实体。判断依据：它有没有自己的一组属性？没有就别拆，拆了只会更复杂。

**② 每个字段问三件事**

| 问 | 例子 | 结论 |
|---|---|---|
| **类型**是什么？ | 金额 | ⚠️ **绝不用小数（Double）**，浮点算钱会出错。存整数最小单位（¥12.50 → 1250） |
| **关系**指向谁？ | 这条账单属于哪个分类 | 存分类的 `id`，不存分类的名字 |
| **来源**是谁？ | 汇率 | 用户手填？系统抓取？还是从别处算出来的？ |

**③ 反推验证（最重要的检查）**

> **拿着这份数据，能不能算出清单里要求的每一个数字？**

逐条对：

- 要「某月总额」 → 得有 `金额` 和 `时间` ✅
- 要「某年总额」 → 同上 ✅
- 要「折算成港币」 → 得有 `币种` + `汇率` ⚠️ **汇率是"当时的"还是"现在的"？**
- 要「按原因搜索」 → 原因得是文本 ✅
- 要「按分类排序」 → 得有分类的稳定排序依据 ⚠️

任何一条答不上来，就是数据模型缺东西 —— 现在补，一行的事；接完数据库再补，就是数据迁移。

**④ 找「隐藏字段」—— 用户不会提、但必须存的**

新手 100% 会漏这三类：

1. **主键 `id`** —— 每条记录得能被唯一指认（用来删、用来改）。
2. **时刻，而不是日期** —— 存的是毫秒时间戳。存 `"2026-10-14"` 字符串的话，你就没法排序、没法按小时看，以后想加新功能会被这个格式卡死。
3. **历史快照类字段** 👈 **最容易被漏、后果最严重**

   > 凡是「现在改了，会让历史数据跟着变」的东西，都要在记录里存一份快照。

   荷包里的例子：
   - 汇率 → 11 月改了汇率，10 月的旧账总额不能跟着变 → **每条账存下当时的汇率**
   - 分类名 → 你把「餐饮」改名成「吃饭」，旧账显示的名字应该跟着变（这个**不该**冻结，因为改名是修正而不是新事实）
   - 但如果是「删掉餐饮分类」，旧账的分类指向就断了 → 要么禁止删除，要么用软删除

**⑤ 关系怎么表示**

| 关系 | 怎么存 | 例子 |
|---|---|---|
| 多对一 | 多的那一边存对方的 id | 多条账单 → 一个分类 |
| 一对多 | 同上（反向看） | 一个分类 → 多条账单 |
| 多对多 | 需要一张「中间表」 | 账单 ↔ 标签（以后要做才需要） |

### 产出

每个实体的字段表（字段名 / 类型 / 约束 / 说明）+ 实体关系说明。

### 验收标准

1. 能算出清单里要求的**每一个**数字。
2. 能回答这个反问：**「如果把某个分类改名，已有记录会怎样？如果删掉它呢？」**

## 阶段 2 · 页面地图 —— 有哪几页、谁进谁出

### 做法

**① 为每个用户故事问：「用户在哪里做这件事？」** → 把故事归并成页面。

**② 一个页面只干一件事。** 如果一页要干两件事，它通常该拆成两页。
（例外：如果真的每次都连着做，强行拆开反而增加点按次数。判断依据是「这两件事是不是总是在同一个时刻发生」。）

**③ 分两类页面：**

| 类型 | 特征 | 导航方式 |
|---|---|---|
| **平级页** | 用户会在它们之间来回切 | 底部页签 / 顶部标签 |
| **钻进页** | 从某页进去、干完就出来 | 点进去 → 返回 |

**④ 数触达次数（量化检查）**

> 最高频的那个动作，从**打开 app** 算起，点几下能完成？
> **超过 3 次就该重构。**

拿荷包举例：「记一笔」是最高频动作。打开 app → 已经在「记一笔」页 → 输入 → 点保存 = **3 次触达**，合格。如果我把「记一笔」藏在「设置 → 记账 → 新增」里，就是 5 次，绝对不行。

### 产出

- 页面清单：每页一句话职责 + 主要元素
- 导航图（纯文本树就够了）

### 验收标准

**每个用户故事，都能在导航图上「走一遍」并且走得通。** 走不通说明缺页面或导航关系错了。

## 阶段 3 · 纵向切片 —— 打通一条端到端最小闭环

### 核心思想

> ❌ **横着切**：先把所有界面做完 → 再写所有逻辑 → 再连数据库
> ✅ **竖着切**：挑**一条**链路，从界面一路捅到数据库，哪怕它丑、哪怕只有 1 个功能

专业上叫 **步行骨架（Walking Skeleton）**。

### 为什么

因为「界面要的数据」和「数据层给的数据」只有撞在一起才知道对不对。

横着切的话，你会在最后才撞上 —— 那时候所有界面都写好了，发现数据模型撑不住，全部返工。
竖着切的话，你在第一天就撞上，改起来还只是几个文件。

### 做法

1. **挑主路径**：最高频 + 被依赖最多的那条。
2. 从界面到数据库整条打通，**不要中途去做别的功能**。
3. 定一个**客观验收条件**，必须能演示。

荷包的验收条件：

> **关掉 app 再打开，刚才记的账还在。**

（这正好是荷包现在缺的那一半 —— 数据还活在内存里。）

### 验收标准

验收条件过了 = 整条技术栈是通的。之后加功能只是「在同一根管子上挂更多东西」，而不是「再挖一条管子」。

## 阶段 4 · 长肉 —— 一次加一个功能

### 做法

**① 排序用三个维度打分：**

| 维度 | 问自己 | 优先 |
|---|---|---|
| **依赖** | 它是别的功能的前提吗？ | 先做被依赖的 |
| **风险** | 哪个最可能做不出来？ | 先做最不确定的 |
| **价值** | 做完哪个用户最能用起来？ | 同分时选它 |

**② 每个功能走一遍小循环：**

```
想清楚（要不要改数据模型？）→ 改数据层 → 改逻辑 → 改界面 → 验证
```

注意第一步是「要不要改数据模型」。**如果这个功能需要新字段，先改模型**，不要等到界面写完了才发现要加字段。

**③ 每加一个功能，都要保证已有的还能跑。**

这就是「回归测试（Regression Test）」的全部含义 —— 不是走形式，是因为**新代码弄坏旧功能**是最常见的 bug 来源。

### 验收标准

新增功能可用，且旧功能没被弄坏。

## 阶段 5 · 打磨上线

新手最常忘的三件事 —— **空状态、错误状态、加载状态**：

| 状态 | 问题 | 荷包的例子 |
|---|---|---|
| **空状态** | 一条数据都没有时，界面显示什么？ | 「还没有记录，上面记第一笔吧」 |
| **错误状态** | 输入非法时给不给反馈？ | 金额输入 `12.345` → 提示「最多两位小数」+ 按钮禁用 |
| **加载状态** | 数据要等的时候显示什么？ | 本地数据库快，暂时不需要；接网络汇率时才需要 |

其余清单：

- **视觉一致性**：配色 / 圆角 / 间距 / 字号有没有**统一来源**（而不是每处手写数值）
- **性能**：列表长了会不会卡？启动慢不慢？掉不掉帧？
- **无障碍**：图标有没有 `contentDescription`？触摸目标够不够大（≥48dp）？
- **打包**：图标、应用名、版本号、签名（调试签名和发布签名是两套）
- **装到**别人的**手机上**试 —— 这才是真测试（你自己手机上的缓存会骗你）
