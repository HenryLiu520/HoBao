## 一、为什么退款不能当收入做

| | 收入 | 退款 |
|---|---|---|
| 钱从哪来 | 外面（工资、红包） | **当初花出去的那笔** |
| 影响什么 | 另算一条线 | **把某笔支出的净额降下来** |
| 能挂在哪 | 独立一条 | 必须挂在原账上 |

用户的原话是「花了 100 退了 20，这笔记账的净支出应该是 80」——
所以退款不是"新的一条账"，是**原账的一个减项**。

## 二、数据模型：子表 + 缓存列

### 子表 `adjustments`

```kotlin
@Entity(
    tableName = "adjustments",
    foreignKeys = [ForeignKey(..., onDelete = ForeignKey.CASCADE)],
    indices = [Index("expenseId")],
)
data class AdjustmentEntity(
    val id: Long, val expenseId: Long,
    val amountMinor: Long,     // 原币最小单位（正数）
    val reason: String, val createdAt: Long,
)
```

一笔账可以退**多次**（先退一半，后来又退剩下的一半），每次有自己的日期和原因。
只存一个"已退总额"的话，这些信息永远丢了。

`onDelete = CASCADE`：删掉那笔账，它的退款一起走。
（对照 `categories` 是 NO_ACTION —— 分类永远不真删。）

### 缓存列 `expenses.refundedCnyCents`

**为什么要冗余一个合计**：支付页、回顾合计、按月小计、桌面组件、分析的四条聚合 SQL，
全都要"净额"。每次都 `LEFT JOIN` 一遍退款表会让每条查询都长一大截，
而且只要有一条漏了 JOIN，就会出现"总额含退款、分类占比不含"这种对不上的数。

**代价**：两份数据要保持一致。所以**只允许经由 `ExpenseRepository.addRefund()` 改它** ——
那个方法在**一个事务**里同时写子表、改缓存列。绕过它直接写 `adjustments`，缓存就会漂移。

> 这是有意的取舍：用"一个写入口"换"十条查询都简单"。

## 三、两道必须守住的规矩

### ① 退款金额是**原币**，折算用**原账冻结的汇率**

买 HKD 100 的东西退 20，退的是 **20 港币**，不是"按今天汇率折的 20 人民币"。

```
refundCny = round(refundMinor × 100 ÷ (10^minorUnits × 原账.ratePerCny))
```

用今天的汇率会出这种事：100 HKD 的消费用 1.09 记（CNY 91.74），
退款时汇率变 1.20，退 100 HKD 折成 CNY 83.33 —— **同一笔买卖，净额不是 0**。

### ② 退款归到**原账所在的时间区间**

退的是 10 月的账，那这 17.03 元就从 10 月的合计里扣，即使退款发生在 11 月。

**后果要说清楚**：退款会**追溯修改**过去区间的数字 —— 昨天看 10 月花了 334.89，
今天退了一笔，再看就变了。这是"净额口径"的必然结果，
和"现金流口径"（退款算退款当月的减项）是两种选择。

选净额的理由：和列表里那一行显示的数字一致 —— 用户看到的就是"这笔账净花了多少"。

## 四、数据库迁移 3 → 4

```sql
CREATE TABLE IF NOT EXISTS `adjustments` ( ... , FOREIGN KEY(`expenseId`)
  REFERENCES `expenses`(`id`) ON UPDATE NO ACTION ON DELETE CASCADE)
CREATE INDEX IF NOT EXISTS `index_adjustments_expenseId` ON `adjustments` (`expenseId`)
ALTER TABLE expenses ADD COLUMN refundedCnyCents INTEGER NOT NULL DEFAULT 0
```

**建表语句必须和 Room 根据 Entity 生成的完全一致**，否则迁移之后 Room 校验结构会直接抛
`IllegalStateException` —— 一开 app 就崩。

## 五、实测：一笔 HKD 退款

在「便利店 HKD 33.33（记作 CNY 28.39，汇率 1.1742）」上退 **HKD 20**：

| 项 | 值 |
|---|---|
| 子表 | `expenseId=6, amountMinor=2000` |
| 缓存列 | `refundedCnyCents=1703` |
| 独立复算 `round(2000×100÷(100×1.1742))` | **1703** ✅ |
| 列表行 | `CNY 11.36` + 「已退 CNY 17.03」 |
| 合计 | 884.89 → **867.86** |
| 本月小计 | 334.89 → **317.86** |
| 分析页总额 | 334.89 → **317.86** |
| 日均 | 15.22 → **14.45** |

**一处改动，七处自动跟着变** —— 因为所有聚合都走同一个净额。

## 六、⚠️ 已知缺口：备份还没带退款

现在的备份格式（`formatVersion 2`）导出的是 `BackupExpense`，
**没有 `refundedCnyCents`，也没有 `adjustments`**。

后果很具体：**导出 → 恢复之后，所有退款会消失，净额变回毛额**。
例如上面那笔，恢复后会从 `CNY 11.36` 变回 `CNY 28.39`。

**为什么没顺手做掉**：adjustments 要引用"哪一笔账"，而文件里账是没有 id 的
（跨设备 id 会变，现在用 `createdAt + amountMinor + currencyCode + categoryName + reason`
这个复合键去重）。所以退款在文件里必须挂在这个复合键上，牵一发动全身：

- `formatVersion` 2 → 3
- `BackupAdjustment` 加进去，用复合键关联
- 导入时先建账再按复合键找 id 插退款
- 老文件（v1/v2）迁移时补一个空数组

**这是下一轮的第一件事。** 在那之前，别拿这个版本的备份当真。
