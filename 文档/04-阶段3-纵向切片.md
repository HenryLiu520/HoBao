| `data/ExpenseRepository.kt` | **唯一数据源** | 界面唯一能碰数据的地方；换成数据库后**接口没变** |
| `viewmodel/ExpenseViewModel.kt` | **状态中心** | 订阅数据库的 Flow，拼好数据给界面 |
| `ui/...` | **界面** | 只负责画，不管数据从哪来 |

**删掉了** `model/Expense.kt` 和 `model/Category.kt` —— 分类从枚举升级成了独立的表。

### ⚠️ 一个诚实的修正

我之前说过「换成数据库，界面代码一行都不用改」。**这句话不准确。**

准确的说法是：

> **分层架构能吸收「实现替换」的变化，但吸收不了「需求变化」的变化。**

- 换存储引擎（内存 → 数据库）→ 确实只改了 Repository 一个文件 ✅
- 但「分类允许用户自定义」是**需求变化**，它把分类从枚举变成了表，界面必然要跟着改 ❌

这不是架构失败，是**架构的能力边界**。别指望架构能吸收需求变化 —— 那要靠流程图（阶段 0~2）提前发现。

## 三、五个核心概念

### ① DAO：只写"我需要什么"，不写"怎么做"

```kotlin
@Dao
interface ExpenseDao {
    @Query("SELECT * FROM expenses ORDER BY createdAt DESC")
    fun observeAll(): Flow<List<ExpenseEntity>>

    @Insert
    suspend fun insert(expense: ExpenseEntity): Long
}
```

**读操作用 `Flow`，写操作用 `suspend`** —— 这个分工不是随便定的：

| | 返回什么 | 为什么 |
|---|---|---|
| 读 | `Flow<List<...>>` | **数据一变，界面自动刷新。**不用手动通知谁去重新查 |
| 写 | `suspend` 函数 | 数据库读写是耗时 IO，必须离开主线程。用 suspend 让**编译器强制**这件事，而不是靠你记得加线程 |

### ② 单向数据流（这是现代 UI 架构的核心）

```
   数据库 ──Flow──▶ ViewModel ──状态──▶ 界面
      ▲                                   │
      └────────── 用户操作 ────────────────┘
```

**界面永远不直接改数据库。** 它只发"意图"（我要记一笔）→ ViewModel 去写数据库 → 数据库变化触发 Flow → ViewModel 状态更新 → 界面重画。

好处：**数据永远只有一个流向，不会出现"界面上是 A、数据库里是 B"的不一致。**

### ③ 依赖注入（手动版）

```kotlin
class ExpenseViewModel(private val repo: ExpenseRepository) : ViewModel()
```

**ViewModel 不自己 `new` 一个 Repository**，而是从构造函数接收（这叫依赖注入）。

为什么？因为要造 Repository 需要数据库，要数据库需要 `Context`，而 `Context` **只有系统能提供**。
所以需要一个"工厂"来把系统给的东西递进来 —— 就是那个 `ViewModelProvider.Factory`。

好处：将来想拿假数据做测试，换个 Repository 传进去就行，这个类一行不用改。

### ④ 数据库必须单例

一个数据库文件被两个 `RoomDatabase` 实例同时打开 → **锁冲突 + 数据不一致**。整个 app 只能有一个。

### ⑤ 播种用 `onCreate` 回调，不能用"表空就播种"

这是个**必须想清楚**的地方：

| 做法 | 后果 |
|---|---|
| "如果分类表是空的就播种" | 用户把 7 个分类全删光 → **下次启动它们全部复活** ❌ |
| `RoomDatabase.Callback.onCreate` | 只有数据库文件**被创建的那一刻**执行一次，之后永不执行 ✅ |

> 教训：**"表空"不等于"没初始化过"。** 判断"是否首次运行"必须用一个只发生一次的事件，
> 而不是一个可以被用户操作改变的状态。

**顺带一个实现细节**：`onCreate` 里只能写裸 SQL，不能用我们自己的 DAO ——
因为回调触发时 Room 实例还在初始化中，DAO 还没准备好。

## 四、这一批踩到的坑

### 1. 版本目录的键名**大小写敏感**

`lifecycleviewmodelCompose` ≠ `lifecycleViewmodelCompose` → `Undefined version reference`。
Gradle 的报错质量很高，会把拼错的键名和所有正确的键名一起列出来。

### 2. 编译通过 ≠ 运行时没问题

我把 ViewModel 的构造函数加了 `repo` 参数，但界面还在用 `viewModel()`（无参版本）。
**编译完全通过**，因为注解处理器和反射都是运行期的事 ——
这种问题会在**启动瞬间崩**。凡是"框架靠反射创建的东西"，编译期都帮不了你。

### 3. "加载中" 和 "空" 是两种状态

数据库还没读完时，界面如果显示"你还没有分类"，就是在**把"等待"误报成"没有"**。

通用规则：

> **任何异步读数据的地方，都有三个状态：加载中 / 有数据 / 确实是空。**
> 少画一个就会出现闪烁或误报。

### 4. 测试方法论：不要拿硬编码数字去断言

我第一版验收脚本写的是「断言界面显示 `HK$179.00 / 共 3 笔`」。
结果第一笔因为冷启动没记进去，**后面所有断言全错**，看起来像 6 个 bug，其实只有 1 个原因。

正确写法：**先抓一次当前状态，操作后再抓一次，对比两次是否一致。**

```python
before = summary()          # 杀掉进程前
hard_restart()
after = summary()           # 重开后
assert before == after      # ✅ 不依赖任何硬编码数字
```

> **凡是能"对比前后"的断言，就不要写"等于某个具体值"。**
> 硬编码的期望值会把"环境差异"和"真的坏了"混在一起，让你花时间查错方向。

### 5. 冷启动比热启动慢很多

刚 `adb install` 完的第一次启动要跑 dexopt/预热，可能比平时慢好几倍。
**测试脚本里等状态，不要等时间** —— 用 `wait_for("餐饮")` 这种轮询，而不是 `sleep(5)` 猜。
