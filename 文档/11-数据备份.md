# 数据备份：导出 / 导入 JSON（阶段 4 · 第 3 项）

> 用户要的三件事：先选文件类型、再定保存格式、最后是"更新后还能导入旧版本"的机制。
> 验收：**全部通过，崩溃 0**

---

## 一、他问的那个机制叫什么

> 「我忘了这个机制叫什么了」

**向后兼容（backward compatibility）** —— 新版本的程序能读旧版本产生的数据。
实现手段叫 **格式版本化 + 迁移链（format versioning + migration chain）**。

三句话就是全部：

1. 文件里带一个整数 `formatVersion`
2. 读到旧版本 → **逐级升级**（v1→v2→v3）→ 升到当前版本再入库
3. 每加一版就加一个迁移器，**旧的迁移器永远不删**

反向的**向前兼容**（旧 app 读新文件）一般做不到，所以必须做到**明确报错**。

## 二、三个决定（用户拍的板）

| # | 项目 | 定稿 |
|---|---|---|
| 1 | 文件类型 | **只用 JSON**（完整备份，含分类 / 币种 / 汇率） |
| 2 | 导入语义 | **两种都做**：合并（默认）+ 覆盖（二次确认） |
| 3 | 分类重名 | **同名直接复用**，没有才新建；**颜色不保存**，名字一样就行 |

## 三、文件格式

```json
{
  "format": "hobao-backup",
  "formatVersion": 1,
  "exportedAt": 1792414789001,
  "appVersion": "0.3",
  "data": {
    "categories": [ { "name": "餐饮", "sortOrder": 0, "isArchived": false } ],
    "currencies": [ { "code": "CNY", "nameZh": "人民币", "symbol": "CN¥",
                      "minorUnits": 2, "ratePerCny": 1.0, "rateUpdatedAt": 0 } ],
    "expenses":   [ { "amountMinor": 2000, "currencyCode": "CNY", "ratePerCny": 1,
                      "reason": "交通", "categoryName": "交通",
                      "createdAt": 1792414789001, "updatedAt": 1792414789001 } ]
  }
}
```

### 四个刻意的选择

| 选择 | 为什么 |
|---|---|
| 分类用 **`categoryName`** 关联，不用 id | id 是自增的，换台设备就变了。名字才是人认得的 |
| 币种用 **ISO 代码** | 全球唯一、天生稳定（和界面上用代码是一致的） |
| **带上 `ratePerCny` 快照** | 不带的话，导回去要按当前汇率重算，历史总额就变了 |
| 金额用**整数** `amountMinor` | 和数据库一致，不引入浮点误差 |
| **不带分类颜色** | 用户定的：颜色不保存。导入时新建的分类按调色板依次取色 |

### 为什么 DTO 和 Entity 分开定义

`BackupModels.kt` 里的 `BackupExpense` 不等于 `ExpenseEntity`。

- 数据库表可以随版本变（加列、改名），但**文件格式一旦发出去就改不回来了** ——
  用户手机里的旧备份永远存在
- Entity 里有设备相关的自增 id，文件里不能有

> **文件格式是对外的契约，表结构是内部的实现。两者绑死，改表就会连带改契约。**

## 四、版本兼容的三条规则

```kotlin
val version = root.optInt("formatVersion", -1)
if (version < 1)                      throw BackupException("备份文件没有格式版本号，可能已损坏")
if (version > CURRENT_FORMAT_VERSION) throw BackupException("来自更新版本的荷包（v$version），请先升级 app")
val migrated = BackupMigrator.migrate(root, version)   // 旧版本逐级升级
```

**规则 A：迁移器只增不改。**
v1→v2 的代码写完之后永远不许动 —— 两年后还有人的手机里躺着 v1 的备份。

**规则 B：只做向后兼容，不做向前兼容。**
旧 app 读新文件做不到，那就必须**明确报错**，绝不能"跳过不认识的字段然后静默导入一半"。

**规则 C：`formatVersion` 和数据库版本号是两件事。**
改表结构不用动文件格式；改文件格式必须 +1 并写迁移器。

## 五、两种导入模式

| 模式 | 做什么 | 安全性 |
|---|---|---|
| **合并** | 追加，按复合键跳过已存在的 | 安全，重复导入不会翻倍 |
| **覆盖** | 先清空三张表，再按文件重建 | 危险，**先弹确认对话框** |

**两种模式都在一个事务里**（`db.withTransaction { }`）。
覆盖模式尤其重要：先 DELETE 再 INSERT，如果中途失败又没有事务，
用户就会既没了旧数据、也没导入新数据 —— 两头空。

**删除顺序必须先子表后父表**（`expenses` 有外键指向 `categories`），否则外键约束会让 DELETE 直接失败。

## 六、判重为什么用「复合键」而不是 uuid

原方案是给 `expenses` 加一列 `uuid`，导入时按它去重。**实现时改掉了。**

原因：加列要动表结构 → 要写真正的数据库迁移 → 一旦迁移写错，用户升级 app 时数据全丢。
而收益只是"判重更严谨"。**风险和收益不对称。**

改用复合键：

```
createdAt + 金额 + 币种 + 分类名 + 原因
```

`createdAt` 精确到毫秒，是同一条账重导时天然相同的稳定指纹。

**代价（记录在案）**：如果导出后手改了某笔账的时间或金额，再导入会被当成新的一笔。

> 通用教训：**能不动表结构就不动。** 表结构的每一次改动都是一次"可能丢光用户数据"的风险。

## 七、文件读写不申请任何权限

用官方 SAF（Storage Access Framework）：

| 操作 | 用什么 |
|---|---|
| 导出 | `ActivityResultContracts.CreateDocument("application/json")`，系统弹"存到哪" |
| 导入 | `ActivityResultContracts.OpenDocument()`，系统弹"选哪个" |

用户选的目录/文件被系统授权给本 app，我们只拿一个 `uri`。
所以清单里**一条存储权限都不用申请** —— `WRITE_EXTERNAL_STORAGE` 从 Android 10 起已经废了。

**职责边界**：ViewModel 只负责「数据 ↔ 文本」，「文本 ↔ 文件」留给界面层。
因为只有界面知道用户选了哪个文件（那是 SAF 的 uri，属于平台细节）。
这样 ViewModel 里没有任何 Android 文件 API，将来要写单元测试也容易。

## 八、踩的两个坑

### 坑 1：Kotlin 的块注释是**可以嵌套**的

我在 KDoc 里写了那个通配 MIME 的字面量，里面的「斜杠 + 星号」被当成 `/*` **又开了一层注释**，
把后面整段代码吞掉了。报错却指向几百行之后的某个括号，完全看不出真正原因。

> **注释里永远不要写"斜杠 + 星号"这个组合。** 真要写就用文字描述。

### 坑 2：MIME 限定太死，文件会变灰选不中

某些文件管理器/网盘把 `.json` 报成 `text/plain` 或 `application/octet-stream`。
导入时 MIME 放开成通配，靠**读出来的内容**判断（`format` 字段）—— 这也更安全，
因为最终还是要校验内容，不能只信文件名。

## 十一、导入时新建的分类，颜色从哪来

**用户问**：「导入后新增了这个类别，没定义颜色，有默认颜色吗？没有的话你加一个」

### 有的，但原来的做法有两个毛病

初版是"第 N 个新建的分类取 `PALETTE[N % 7]`"（7 色调色板依次分配）：

| # | 毛病 | 后果 |
|---|---|---|
| 1 | 调色板只有 7 个色 | 第 8 个分类开始必然重复 |
| 2 | 合并导入时新分类**从第 0 色开始取** | 设备上已有的 7 个分类正好占满调色板 → **必然撞色** |

### 改成：颜色由分类名推出来

```kotlin
private fun colorForName(name: String): Long {
    val hue = (name.hashCode().toLong() and 0x7FFFFFFFL) % 360L
    val argb = android.graphics.Color.HSVToColor(floatArrayOf(hue.toFloat(), 0.55f, 0.62f))
    return argb.toLong() and 0xFFFFFFFFL
}
```

**三个好处：**

1. **无限种颜色** —— 不再受调色板大小限制
2. **同一个名字永远同一个颜色** —— 换设备、重导、清库重装都一样
3. **文件里依然不用存颜色**（用户的要求），颜色是**算出来的**，不是存出来的

⚠️ 用的是 `String.hashCode()`。它在 Java 规范里被**明确规定**了算法，
所以跨设备、跨版本、跨 JVM 结果完全一致 —— 这是它能当"稳定种子"的前提。
（`Kotlin Random`、对象地址、默认 `hashCode` 实现都不行，那些每次运行都不一样。）

S/V 压到 0.55 / 0.62：这是个 10dp 的小圆点，太艳会刺眼。

### 合并 vs 覆盖，颜色行为不一样（记录在案）

| 模式 | 已有分类 | 新建分类 |
|---|---|---|
| **合并** | 复用设备上的那个，**颜色保持原样** | 由名字推色 |
| **覆盖** | 全部清空重建 | 全部由名字推色 |

**所以同一个备份，覆盖导入后原有分类的颜色会和合并导入不一样** ——
这是"颜色不存文件"的必然结果，不是 bug。如果以后想让两边一致，
可以把新安装时的播种颜色也改成 `colorForName`，那样三处就统一了。
