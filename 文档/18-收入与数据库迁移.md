# 18 · 收入（反向记账）与数据库迁移

> ⚠️ **已被 `20-两本账.md` 取代**。本文记录的是「收入用 `kind=1` 和花销同表」的旧设计；
> 2026-10-22 已重构为收入独立成表（数据库 v5）。本文保留作历史，代码不要照做。


> 2026-10-22 · 用户原话：「加一个功能，就是可以反向记账，+钱这样，看看怎么处理」
>
> 这一轮真正做的事有两件：**先做迁移地基**，再做收入。顺序反了会丢数据。

---

## 一、先把「加钱」拆成三种

| 语义 | 例子 | 该挂在哪 | 对"这个月花了多少" |
|---|---|---|---|
| **收入** | 工资、奖学金、红包 | 独立一条 | 不影响；另算 |
| **退款** | 耳机退了 129.90 | 挂在原来那笔账上 | 净支出 ↓ |
| **返现** | 信用卡月底返 50 | 可挂可不挂 | 净支出 ↓ |

**为什么不做一个 `+号` 了事**：收入 3000 和 退款 3000 在统计里会长得一模一样 ——
一个是"我挣了 3000"，另一个是"我退了一笔 3000 的东西"。月底看净额分不清。

> 符号不携带语义。金额的正负只回答"加还是减"，不回答"为什么加"。

用户拍板：**两种都要，但分两轮**。这一轮只做**收入**；退款挂在原账上属于另一件事
（见 `文档/15-待办-备注与退款.md` 的 C 项）。

## 二、数据模型：为什么加列而不是存负数

| | 做法 | 要迁移 | 优点 | 代价 |
|---|---|---|---|---|
| A | 收入存**负金额** | 不用 | 所有 SUM 天然正确 | UI 到处漏负数；分类占比出现**负的饼图片**；"工资"被算成"负的餐饮" |
| **B** | 加一列 `kind` | 要 | 语义清晰，界面能分家 | 聚合要按 kind 分桶 |
| C | 独立 `incomes` 表 | 要 | 彻底隔离 | 代码翻倍；退款挂账难 |

选 **B**：`amountMinor` 恒为正，`kind` 决定语义（0 支出 / 1 收入）。

SQL 里三种口径从同一次查询出来，不会各算各的：

```sql
总支出 = SUM(CASE WHEN kind = 0 THEN cny ELSE 0 END)
总收入 = SUM(CASE WHEN kind = 1 THEN cny ELSE 0 END)
```

## 三、数据库迁移 2 → 3（这一轮的地基）

### 改了什么

```kotlin
db.execSQL("ALTER TABLE expenses   ADD COLUMN kind INTEGER NOT NULL DEFAULT 0")
db.execSQL("ALTER TABLE categories ADD COLUMN kind INTEGER NOT NULL DEFAULT 0")
insertIncomeCategories(db)   // 老用户升级也要有「工资」这些分类
```

同时：
- `version = 2 → 3`
- `exportSchema = false → true`，并把 `room.schemaLocation` 指到 `app/schemas`
  （每个版本的结构会写成 JSON，写迁移和迁移测试都要靠它）
- **删掉 `fallbackToDestructiveMigration`**，换成 `.addMigrations(MIGRATION_2_3)`
- 删掉 `onDestructiveMigration` 回调 —— 迁移是真的了，不会再有"删库"这条路径，
  留着反而会让"迁移失败"看起来像正常行为

### 为什么 `DEFAULT 0` 让迁移变简单

老数据全部变成"支出"，**语义上天然正确，一条 UPDATE 都不用写**。
这就是"加列"比"改语义"安全的地方。

### 真机验收（这个必须实测，不能靠推理）

| | 升级前 | 升级后 |
|---|---|---|
| `user_version` | 2 | **3** |
| expenses 行数 | 9 | **9** |
| `SUM(amountMinor)` | 87303 | **87303** |
| categories | 7 | **12**（+5 个收入类） |
| 崩溃 | — | **0** |

做法：装旧版 → 记 9 笔 → **不卸载**直接装新版 → 查库比对。

## 四、收支分家后的各处口径

| 位置 | 口径 |
|---|---|
| 记一笔 | 顶部 `− 支出 / + 收入` 切换；分类列表跟着换一套 |
| 分类 | `categories.kind`：7 个支出类 + 5 个收入类（工资/奖金/红包/利息/其他收入） |
| 本月小计 | **只算支出**；收入另起一行，且只在 > 0 时显示 |
| 回顾合计 | 支出（大字）+ 「收入 +X · 净 −Y」一行 |
| 月分组小计 | **只算支出**，并且标成「支出 CNY xxx」 |
| 列表行 | 收入行加 `+` 前缀 + 绿色 |
| 分析页 | **只算支出**；收入在总额下面一行小字「同区间收入」 |
| 桌面组件 | 今日开销只算支出 |
| 快速记账小窗 | 只列支出分类 |

**净额必须由"支出 − 收入"算出来**，不能另外累加 —— 否则两边口径一旦不同，
会出现"支出 100、收入 20、净额 79.99"这种没人能解释的差。

## 五、备份格式 1 → 2

- `CURRENT_FORMAT_VERSION = 2`，`BackupCategory` / `BackupExpense` 各加 `kind`
- 迁移链里补 `migrateV1ToV2`：老文件的每条账/每个分类补 `kind = 0`
- 编码时写出 `kind`；解码时 `optInt("kind", 0)` 兜底

**单测（`BackupFormatMigrationTest`，5 条全过）**：

| 用例 | 结果 |
|---|---|
| v1 文件没有 kind → 补成支出 | ✅ |
| v1 里的账一分不少 | ✅ |
| 导出的文件带 formatVersion 2 和 kind | ✅ |
| 导出再导入，kind 不丢 | ✅ |
| 更新版本的备份要明确报错 | ✅ |

## 六、这一轮踩的坑（值得单独记）

### 批量替换漏掉一条 SQL —— 而且不报错

给三条分析 SQL 加 `AND e.kind = 0`，我用了批量替换，匹配串是
`"WHERE e.createdAt >= :from AND e.createdAt < :to " `（**带尾空格**）。

结果 `analysisTotal` 那行结尾没有空格 → **没被匹配到**。

现象：

```
分析页总额   CNY 5,334.89     ← 334.89 + 5000（收入混进来了）
分类占比     购物 158.29 / 餐饮 127.16 / 交通 49.44   ← 这些是对的
```

两个数各自看着都正常，但**加起来对不上**。而且分类占比那条有过滤、总额那条没有，
说明它们走了两条口径 —— 这正是我在这份文档里反复强调的那种 bug。

> 教训：批量替换之后要**逐条确认命中数量**，别只看"替换成功"。
> 更稳的做法是让三条查询共用同一个 WHERE 常量，从源头上不可能不一致。

### 天数写死的测试会隔天就红

模拟器的日期从 10/20 走到 10/22，回归脚本里写死的「共 20 天 / 日均 16.74」立刻全红。
改成按 `date.today()` 现算期望值。

> 测试里的期望值分两类：**业务常量**（334.89 这种）可以写死，
> **时间派生的值**（天数、日均）必须现算。

## 八、下一轮

退款/返现（挂原账）—— `文档/15` 的 C 项。设计上要用**子条目**：

```
adjustments(id, expenseId, amountMinor, reason, createdAt)
净额 = 原金额 − 该账下的 adjustments 合计
```

`expenseId` 允许为空 → 支持"没挂账单的返现"（银行月底返现）。
