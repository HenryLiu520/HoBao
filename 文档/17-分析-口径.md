## 一、这一页要回答三个问题

1. **这段时间花了多少？**（总额 / 笔数 / 日均）
2. **钱花在哪？**（分类占比）
3. **花得比之前多还是少？**（区间的逐期趋势）

超出这三个的（同比环比、异常检测、预算对比、报表导出）**本轮不做**。

| # | 口径 | 决定 | 为什么是这个 |
|---|---|---|---|
| 1 | **时间范围** | 可切换：本周 / 本月 / 本季 / 本年，复用 `TimeFilter` | 代码已经有了，不重造 |

| 4 | **用哪个汇率** | 每条账**自己冻结的** `ratePerCny` 快照 | 用"今天的汇率"会让历史图每天变 —— 那就不叫历史了 |

| 6 | **分类** | 按 `categoryId` 分组；**归档分类照常计入** | 钱花了就是花了。归档只是"以后不用"，不是"以前没花" |

| 9 | **单一分类** | 环形图退化成整圆，图例照常显示 | 一个分类 100% 也是有效信息 |
| 10 | **趋势粒度** | 区间 ≤ 62 天 → 按**天**；> 62 天 → 按**月** | 一年按天画是 365 根柱子，没法看 |
| 11 | **退款/负数** | 本轮没有；口径预留成「净额」，将来 `adjustments` 表落地后改 | 现在就写死"毛额"，将来要改每一处 |
| 12 | **时区** | 一切按**设备本地时区** | 和在港生活的实际感受一致；跨时区旅行时以手机为准 |

## 四、SQL 定稿（已验证）

```sql
SELECT e.categoryId,
       SUM(CAST(ROUND(
             e.amountMinor * 100.0 /
             ((CASE c.minorUnits WHEN 0 THEN 1.0 ELSE 100.0 END) * e.ratePerCny)
           ) AS INTEGER)) AS cnyCents,
       COUNT(*) AS cnt
FROM expenses e
JOIN currencies c ON c.code = e.currencyCode
WHERE e.createdAt >= :from AND e.createdAt < :to
GROUP BY e.categoryId
ORDER BY cnyCents DESC
```

### 三个必须写进注释的坑

**① 括号不能省 —— 我第一版就写错了**

```sql
-- ❌ 错：除法和乘法同级，从左到右结合
e.amountMinor * 100.0 / (CASE ... END) * e.ratePerCny
--   实际算的是 (amountMinor * 100 / X) * rate

-- ✅ 对：要整体除
e.amountMinor * 100.0 / ((CASE ... END) * e.ratePerCny)
```

实测差多少：**3 个分类里 2 个错，合计 23,583 元 vs 404 元，差 58 倍。**

**② `ROUND` 必须在 `SUM` 里面**

项目的语义是「每条账各自舍入一次，再相加」。放到外面就变成「先相加再舍入」。

实测（三笔日元 1 元、汇率 3.0）：

| 写法 | 结果 |
|---|---|
| 逐条舍入再相加（✅ `Money.kt` 的语义） | **99 分** |
| 先相加再舍入（❌） | 100 分 |

**差 1 分。** 这种差不会报错，只会让"合计"和"分析页"对不上，而且你几乎不可能靠肉眼找出来。

**③ `CASE minorUnits` 是在绕开 SQLite 没有 `POWER()`**

现在只有 0（日元）和 2（其他）两种情况。**这是个隐式约定** ——
将来要加三位小数（例如某些中东货币），这里必须一起改，否则分析页会静默算错。

## 八、实现中又发现并修掉的三处口径 bug

### bug 3：「日均」的分母把未来日子算进去了

按 `[本月起, 下月起)` 算天数是 31 天 —— 但今天是 20 号，未来 11 天不可能有账。

| 分母 | 日均 |
|---|---|
| 31 天（错） | CNY 10.80 |
| **20 天（已过的天）** | **CNY 16.74** |

**差 55%**，而且会随着日子推进天天变。

修法：`daysIn()` 取 `min(区间结束, 今天 + 1)`。

### bug 4：趋势图出现了未来的日期

第一版截图里，趋势是 `10/20 10/21 10/22 …` —— 全是 0.00。
因为补零补到了区间结束（11 月 1 日），真正有数据的日子被挤出了可视区。

修法：`buildTrend()` 用同一个 `min(区间结束, 今天 + 1)` 收尾。

> 这两条是**同一个思维错误的两处表现**：把「区间的数学终点」当成了「真实的终点」。
> 凡是「本期」类指标，分母和坐标轴都得裁到今天。

### bug 5：「按今日汇率折算」这个标签是错的

`AddExpenseScreen` 的汇总卡写着「共 N 笔 · 按今日汇率折算」，
但实际用的是**每条账记账当时冻结的汇率快照**（改汇率不会动历史账）。

改成「按记账时汇率折算」。

> 标签写错和数字算错一样危险 —— 用户会据此推断错误的事
> （比如以为改汇率能让历史账跟着变）。

## 十、附：验证环境的三个坑（下次直接用）

1. **Room 是 WAL 模式**：主库 `hobao.db` 可能只有 4096 字节，数据全在 `hobao.db-wal`（65 KB）。
   只 `cat hobao.db` 会拿到一个空库 —— 必须把 `-wal`、`-shm` 一起拉，本机 `sqlite3` 打开时自动回放。
   改完后 `PRAGMA wal_checkpoint(TRUNCATE)` 把 WAL 并回主库，再推回去。
2. **`run-as` 读不了 `/data/local/tmp`**：app 用户没有那个目录的权限。
   `adb push` 到 `/data/local/tmp` 再 `run-as cp` 一定失败。
   正解：`adb shell "run-as <pkg> dd of=databases/hobao.db" < 本地文件`。
3. **重定向必须在 `run-as` 里面**：`adb shell run-as pkg "cat > databases/x.db"` 里的 `>`
   是**设备端 shell（shell 用户，cwd = /）**执行的，会往 `/databases/` 写。用 `dd of=` 绕开。

## 十一、第 4 步：画图（2026-10-20）

### 决定：折线用库，环形自己画

| 图 | 做法 | 理由 |
|---|---|---|
| 趋势 | **Vico 3.2.3** 折线 | 刻度取整、标签避让、缩放、边界裁切 —— 细节多但没意思，正是库的价值 |
| 分类占比 | **Compose Canvas 手写**（约 30 行） | 环形图的几何就是 `角度 = 占比 × 360°`，为一个乘法拖进几百 KB 不值 |

> **判断标准不是"库好不好"，而是这段逻辑是不是本质复杂。**

### 环形图为什么是环形、为什么保留列表

- **环形**：中间挖空能放总额（实心饼塞字就是灾难）
- **不加片上标签**：分类最多 7 个，外置标签会互相压
- **下方列表保留**：图回答"哪块最大"，列表给**能被引用的精确数字**，也是色盲用户唯一能读的通道
- 颜色用**分类自己的色**（`colorArgb`），不是主题配色 —— 同一个分类在环形、列表圆点、账单卡片里永远是同一个色

### 折线图为什么是折线不是柱状

横轴是**连续时间**（天/月）。折线表达"变化和斜率"，柱状表达"每一次各是多少"。
记账趋势关心的是"是不是在往上走"，所以折线更对。

（分类占比那种**离散对比**才适合柱状。）

## 十二、这一轮踩的三个坑（都不是"写错代码"）

### 坑 1：Vico 3.3.1 用的是 Kotlin 2.4，本项目编译不了

```
e: Module was compiled with an incompatible version of Kotlin.
   The binary version of its metadata is 2.4.0, expected version is 2.2.0.
```

AGP 9.4.1 内置 Kotlin 2.2.10，编译器只能读到元数据 2.3.0。

| Vico | 编译用 Kotlin | 有 PieChartHost | 本项目可用 |
|---|---|---|---|
| 3.3.1 | 2.4.10 | ✅ | ❌ |
| **3.2.3** | 2.3.21 | ❌ | ✅ |

**饼图只在新版有，而新版要升整个构建链的 Kotlin。**

> 教训：**库的版本不是越新越好，先看它和你的构建链兼不兼容。**
> 顺带也说明了"该自己画的就自己画"的价值 —— 如果环形图也依赖库，这个功能会被版本卡死。

### 坑 2：formatter 返回空串 → Vico 直接抛异常

抽稀横轴标签，我第一版是"不需要显示的返回空字符串"：

```kotlin
if (i % step == 0) labels[i] else ""      // ❌
```

```
java.lang.IllegalStateException: `CartesianValueFormatter.format` returned a blank string.
Use `HorizontalAxis.ItemPlacer` and `VerticalAxis.ItemPlacer` ...
```

而且它是在 **绘制阶段**抛的，堆栈里从头到尾都是 Compose 的 `draw`，看不到一行自己的代码。

正解：

```kotlin
itemPlacer = HorizontalAxis.ItemPlacer.aligned(spacing = { step })   // ✅ 用它控制抽稀
valueFormatter = CartesianValueFormatter { _, v, _ -> labels.getOrNull(v.toInt()) ?: "" }  // 只做翻译
```

### 坑 3（最隐蔽）：默认缩放把数据截断了，而且不报错

一个月的折线图只画出**前 10 天**，纵轴顶到 120（真实最大值是 129.90），
横轴标签只有 10/01、10/05、10/09 —— 看起来完全正常。

原因在默认值：

```kotlin
initialZoom = Zoom.max(Zoom.fixed(), Zoom.Content)   // Zoom.fixed() 默认 1f
```

`max(1.0, Content)` 的意思是：**装得下就装，装不下也不缩小**。
20 个点需要缩到 1× 以下才放得下，被 `1f` 卡住 → 只显示能塞进 1× 的那部分。

而「本年」只有 10 个点，1× 刚好装得下，**所以同一个 bug 在另一张图上完全不出现**。

修法：

```kotlin
val zoomState = rememberVicoZoomState(zoomEnabled = false, initialZoom = Zoom.Content)
```

> 教训：**"默认值"是别人替你做的决定。** 这类 bug 的共同点是 ——
> 不崩、不报错、不告警，只是**少给你一部分数据**。
> 发现它的唯一办法是拿真实数字去对（10/15 那笔 129.90 画不出来才露的馅）。

## 十五、横轴粒度 + 可滑动（2026-10-20 追加）

### 需求

> 趋势改为可以滑动，然后可以调整横轴大小，日周月季度年

### 粒度只影响"怎么分组"，不影响总额

聚合仍然只下沉到「天」（`dailySums` 一条 SQL）。周/月/季/年都是**天的容器**，
在内存里折叠 ≤366 行没有性能问题，却省掉四条几乎一样的 SQL（每条还要各自处理时区、边界、补零）。

**必须守住的不变式**：换粒度之后，所有桶加起来必须还是同一个数。

| 区间 | 日 | 周 | 月 |
|---|---|---|---|
| 本月（10/1–10/20） | 20 个桶 · CNY 334.89 | **4 个桶** · 334.89 | 1 个桶 · 334.89 |

周的四个桶（实测，和 Python 独立算的一致）：

```
2026-09-28   CNY  42.00    ← 10/01 落在这周
2026-10-05   CNY 126.60    ← 10/05 85.16 + 10/08 41.44
2026-10-12   CNY 166.29    ← 10/12 8.00 + 10/15 129.90 + 10/18 28.39
2026-10-19   CNY   0.00
```

### 分桶规则（对齐自然单位，不按"距今多少天"切）

| 粒度 | 桶的起点 | 标签 |
|---|---|---|
| 日 | 当天 | `10/05` |
| 周 | **周一**（和 `TimeFilter.ThisWeek` 一致） | `10/05`（那周的周一） |
| 月 | 1 号 | `10月` |
| 季度 | 1 / 4 / 7 / 10 月的 1 号 | `Q4` |
| 年 | 1 月 1 日 | `2026` |

### 退化：粒度比区间还粗时只有 1 个桶

「本月 + 月」「本年 + 年」= 1 个数据点。折线图对 1 个点是**什么都画不出来**的 ——
一根空白坐标系看起来就是坏了。

处理：不禁止这个选项（"这个月一共花了多少"本身是合理的问题），
换一种表达方式回答它 —— 中间显示那个数，下面写「这个粒度下只有 1 个数据点，换成日或周才有曲线」。

### 自动默认 vs 用户选择

- 首次进入：本周/本月 → 日；本季/本年 → 月
- **用户手动选过之后，切区间不再覆盖**（选了「日」再切本年，就看一年里的每一天，可滑动）
- 只有没手动选过时才跟着区间自动调

## 十六、滑动的三个坑（连着的，一个比一个深）

### 坑 4：`initialScroll = Scroll.Absolute.End` 完全不生效

`VicoScrollState.update()`：

```kotlin
if (!initialScrollHandled) {
    value = initialScroll.getValue(context, layerDimensions, bounds, maxValue)
    initialScrollHandled = true          // ← 第一次就置位
}
```

**第一次布局时模型还没到**，`maxValue = 0` → value 被钉在 0，
然后 `initialScrollHandled` 立刻变 true，之后再也不处理。

表现：明明写了 `End`，图却停在最左边（实测停在 1 月 1 日）。

### 坑 5：`autoScroll` 也不行，它在缩放生效前就算完了

改用 `autoScroll = Scroll.Absolute.End` + `autoScrollCondition = { _, _ -> true }`，
首次打开是对的。但**切换粒度**（周 4 个点 → 日 20 个点）时又回到最左边：
内容突然变宽，`maxValue` 在缩放应用之前就被取走了。

### 坑 6：正解 —— 模型落定后等两帧，再显式滚

```kotlin
LaunchedEffect(trend) {
    producer.runTransaction { lineModel { series(...) } }
    withFrameNanos { }        // 一帧：把新模型量出来
    withFrameNanos { }        // 一帧：把新缩放的 layerDimensions 应用上去
    scrollState.scroll(Scroll.Absolute.End)
}
```

少等一帧，`scroll()` 拿到的还是旧 `maxValue`，等于没滚。

### 附带：纵向滚动没被吃掉

图表在 `verticalScroll` 的 Column 里。实测**在图上纵向滑动，页面照常滚** ——
Vico 只消费横向拖拽。这条要专门测，因为"图表吞掉页面滚动"是最常见的嵌套滚动事故。
