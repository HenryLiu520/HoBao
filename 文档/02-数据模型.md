## 一、推导过程（不是凭空写的）

**做法：逐条读用户故事，把名词圈出来。**

| 用户故事 | 圈出的名词 | 是一个独立实体，还是只是字段？ |
|---|---|---|
| M1 记一笔（金额 + 原因 + 分类） | **账单**、分类、金额、原因 | 账单 = 实体；分类 = 见下 |
| M3 用外币记账，按自填汇率折算 | **货币**、汇率 | 货币有自己一组属性（符号、小数位）→ **实体** |
| M4 按月/年看总额 | 月份 | 不是实体，从账单的时间字段**算**出来 |
| M5 按原因搜索 | 原因 | 只是账单上的一个字段 |
| M6 筛选（时间 + 排序） | — | 不是实体，是**查询参数**，不存 |
| M7 分类自定义 | **分类** | 有自己一组属性（名字、颜色、顺序）→ **实体** |
| S1 修改记录 | — | 只是给账单加一个"最后修改时刻"字段 |

**结论：三个实体 —— 账单 / 分类 / 货币。**

判断「独立实体 vs 字段」的唯一标准：

> **它有没有自己的一组属性？有就独立成实体，没有就只是一个字段。**
>
> 例：货币有符号、小数位数、汇率 → 独立。
> 　　月份没有属性，它是从时间算出来的 → 不独立。

## 二、实体一：`expenses`（账单）

| 字段 | 类型 | 约束 | 说明 | 追溯 |
|---|---|---|---|---|
| `id` | Long | 主键，自增 | 唯一标识，用来删/改 | 所有故事 |
| `amountMinor` | Long | 非空 | **整数，最小货币单位**。HK$12.50 → `1250`；¥980（日元无小数）→ `980` | M1 |
| `currencyCode` | String | 非空 | ISO 4217，如 `"HKD"` `"JPY"`。**不存符号（`HK$`），符号是显示时才拼的** | M3 |
| `rateToHkd` | Double | 非空 | **汇率快照**：记账当时 1 单位该币 = 多少港币。港币本身 = `1.0` | M3 |
| `reason` | String | 非空 | 原因 / 备注 | M1 |
| `categoryId` | Long | 非空，外键 | 指向 `categories.id`。**存 id，不存名字** | M1 / M7 |
| `createdAt` | Long | 非空 | **毫秒时间戳**（记账那一刻），不是 `"2026-10-14"` | M1 / M4 |
| `updatedAt` | Long | 非空 | 最后修改时刻 —— **由「S1 允许修改」这条需求带来的新字段** | S1 |

### 三个关键决定

**① 金额为什么必须是整数？**

浮点数算钱会出错：`0.1 + 0.2 = 0.30000000000000004`。钱必须精确，所以存整数最小单位，显示时才除。

**② 为什么港币也要存 `rateToHkd`？**

统一逻辑。如果港币特殊处理（不存汇率），那所有算总额的地方都要写 `if (currency == "HKD")`。让它等于 `1.0`，公式就永远只有一条：

```
港币金额 = amountMinor / 10^minorUnits × rateToHkd
```

**③ `updatedAt` 是怎么冒出来的？**

需求清单里没有任何一条用户故事提到它。这是**「允许修改」这条需求的必然产物** —— 你既然能改，就得知道什么时候改的。

> **这就是「隐藏字段」的现实版：需求不会直接告诉你需要它，但需求会逼出它。**

## 三、实体二：`categories`（分类）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | Long | 主键，自增 | |
| `name` | String | 非空，唯一 | 显示名，如「餐饮」 |
| `colorArgb` | Long | 非空 | 颜色，存 ARGB 整数（如 `0xFFE8760B`） |
| `sortOrder` | Int | 非空 | 显示顺序。「按分类排序」时用它，**不用 id**（id 是内部标识，不该被用户感知） |
| `isArchived` | Boolean(O=0/1) | 非空，默认 0 | **软删除标记**。见下方「删除分类」 |
| `createdAt` | Long | 非空 | 创建时刻 |

### 为什么不能直接删掉一个分类？

考虑这个场景：用户记了 100 笔「餐饮」，然后想把「餐饮」删掉。

| 做法 | 后果 |
|---|---|
| **硬删除**（真的从表里删掉） | 那 100 条账的 `categoryId` **指向了一个不存在的 id** → 界面上显示不出来 / 程序崩 / 数据变成孤儿 |
| **软删除**（`isArchived = 1`） | 旧账照样能显示分类名；但「新增记账」的可选列表里不再出现它 |

> **这是真实工程里最重要的一条设计直觉：**
> **「删除」往往不是真的删，而是「不再出现在可选列表里」。**

（数据库还有更硬的方案叫「外键约束 + ON DELETE 行为」，但 SQLite 默认不开外键约束，而且这里策略上是"保留历史"，所以软删除更合适。）

## 四、实体三：`currencies`（货币与汇率）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `code` | String | **主键** | `HKD` / `CNY` / `JPY` / `USD` / `EUR` / `GBP` / `TWD` / `KRW`… |
| `nameZh` | String | 非空 | 中文名「港币」 |
| `symbol` | String | 非空 | `HK$` / `¥` / `$` |
| `minorUnits` | Int | 非空 | **小数位数**：HKD = 2，JPY = **0**，KRW = 0 |
| `rateToHkd` | Double | 非空 | 用户手动填的当前汇率。HKD 自己固定 `1.0` |
| `isEnabled` | Boolean | 非空，默认 0 | 是否出现在「记账」的币种选择里 |
| `sortOrder` | Int | 非空 | |

### 为什么 `minorUnits` 是必须的字段（容易漏）

把整数还原成显示金额时：

```
显示金额 = amountMinor / 10^minorUnits    然后保留 minorUnits 位小数
```

- HKD：`1250 / 10^2 = 12.50` ✅
- JPY：`980 / 10^0 = 980` ✅（日元没有「分」，写成 `980.00` 是错的）

**如果漏了这个字段，所有金额格式化都会把日元显示成「980.00 円」** —— 这就是"需求里没提、但不做就错"的典型隐藏字段。

### 汇率的两个位置（别搞混）

| 存在哪 | 是什么 | 用途 |
|---|---|---|
| `currencies.rateToHkd` | **当前**汇率 | 记账时自动带出来，作为快照的初始值 |
| `expenses.rateToHkd` | **历史**快照 | 计算总额时用它，**永远不跟着改** |

> **这条是整个数据模型里最重要的一个决定：**
> 同一份「汇率」数据存两处，一处是"现在的"，一处是"当时的"。
> 因为**汇率是事实的一部分，不是当前状态的查询**。11 月改了汇率，10 月的旧账总额绝不能跟着变。

## 五、关系图

```
                    ┌─────────────────┐
                    │   currencies    │
                    │  code (PK)      │
                    │  rateToHkd      │
                    │  minorUnits     │
                    └────────┬────────┘
                             │ 逻辑外键：expenses.currencyCode → currencies.code
                             │ （不强制，因为币种集合稳定、且历史账不能因为币种被删就坏）
                             ▼
        ┌──────────────────────────────┐
        │         expenses             │
        │  id (PK)                     │
        │  amountMinor                 │
        │  currencyCode                │
        │  rateToHkd   ← 历史快照       │
        │  reason                      │
        │  categoryId ─────────┐       │
        │  createdAt           │       │
        │  updatedAt           │       │
        └──────────────────────┼───────┘
                               │ 外键（多对一）
                               ▼
                    ┌─────────────────┐
                    │   categories    │
                    │  id (PK)        │
                    │  name           │
                    │  isArchived     │
                    └─────────────────┘
```

**「多对一」怎么表示：多的那一边存对方的 id。** 多条账单 → 一个分类，所以 `expenses.categoryId` 存分类 id。

## 六、反推验证（阶段 1 的出口条件）

> 拿这份数据，能不能算出清单要求的每一个数字？

| 需求 | 靠什么算 | 通过？ |
|---|---|---|
| 本月总额 | `SUM(amountMinor / 10^minorUnits × rateToHkd)`，`WHERE createdAt ∈ 本月` | ✅ |
| 某年总额 | 同上，换成年的范围 | ✅ |
| 某月小计（分组头） | 同上，按 `createdAt` 的月份 GROUP BY | ✅ |
| 按原因搜索 | `WHERE reason LIKE %关键词%` | ✅ |
| 按金额排序 | `ORDER BY amountMinor × rateToHkd`（要按折算后的港币排，否则「100 日元」会排在「12 港币」前面 —— **跨币种排序必须折算后才能比大小**） | ✅ |
| 按分类排序 | `ORDER BY categories.sortOrder` | ✅ |
| 一次性显示所有分类 | `WHERE isArchived = 0 ORDER BY sortOrder` | ✅ |
| 筛选"不限" | 不加时间条件 | ✅ |
| 筛选"从第一笔记账起" | `MIN(createdAt)` 作为滚轮/日历的下界 | ✅ |

**额外检查：改分类名会不会影响旧账？**
改名 → 旧账跟着变（因为存的是 id，显示时 join）✅ **符合预期**
删除分类 → 旧账不受影响（软删除）✅

**额外检查：改汇率会不会影响旧账总额？**
不会。旧账用的是自己存的 `rateToHkd` 快照 ✅ **符合预期**

## 七、已定决策

| # | 问题 | 决定 | 连带影响 |
|---|---|---|---|
| 1 | 删在用分类时旧账怎么办 | **软删除**（`isArchived = 1`） | 所有「取分类列表」的查询都要带 `WHERE isArchived = 0` |
| 2 | 默认开启哪些币种 | **HKD / CNY / JPY / USD / EUR / GBP**（六种） | 首次启动要往 `currencies` 表播种这 6 行；HKD 的 `rateToHkd` 固定 `1.0` |
| 3 | 自带 7 个分类能否改名/改色/删除 | **能改也能删** | 见下方「边界情况」 |

### 首次启动的播种数据（Seed）

app 第一次运行时要往数据库里写初始数据，否则用户打开就是空的：

- `categories`：餐饮 / 交通 / 购物 / 住宿 / 学习 / 娱乐 / 其他（7 条，带各自的颜色和 `sortOrder`）
- `currencies`：上表 6 条，`isEnabled = 1`；HKD 的 `rateToHkd = 1.0`

**做法上要注意：** 播种只能在**数据库第一次被创建时**执行一次，不能每次启动都执行（否则用户删掉的分类会"复活"）。
Room 提供 `RoomDatabase.Callback.onCreate` 正是干这个的。

### ⚠️ 由「能改也能删」引出的边界情况

**问题：** 如果用户把 7 个分类**全删光**，「记一笔」页没有分类可选 —— 而 `expenses.categoryId` 是非空外键 —— **一笔记账都记不了，app 变砖。**

**这是「允许删」这个决定的必然代价，不是 bug。**

**处理方式（不改决定，加兜底）：**

1. 允许删光。
2. 「记一笔」页在「可用分类数量 = 0」时：
   - 分类行显示引导文字：「还没有分类，去 **设置 → 分类管理** 建一个」
   - 「记一笔」按钮**禁用**
3. 这与现有规则一致（金额非法时按钮也禁用），不引入新概念。

> **通用教训：每一个"允许用户做 X"的决定，都要问一句「那用户把 X 做到极端会怎样？」**
> 允许删 → 删光了怎么办；允许填 0 → 金额 0 的账要不要；允许超长文本 → 原因 1 万字怎么显示。
> **边界情况不是等测试来发现的，是在拍决定的那一刻就该想出来的。**

## 八、这张表怎么变成代码（剧透，进阶段 3 才做）

Room 的三个角色，跟本文档一一对应：

| 本文档 | 代码里叫什么 | 作用 |
|---|---|---|
| 实体（三张表） | `@Entity` 数据类 | 描述"存什么" |
| 实体之间的关系 | 数据类里的外键字段 | 描述"谁指向谁" |
| 你需要的每种查询 | `@Dao` 接口里的方法 | 描述"怎么取" |
| 整个数据库 | `@Database` 抽象类 | 把上面三个绑在一起 |
