# 20 · 两本账：花销/退款 vs 收入

> 2026-10-22。把「三种款项」重构成「两本账」。
> 数据库 v4 → **v5**，备份格式 v2 → **v3**。

---

## 一、为什么要改

上一轮做退款时，三种款项是这样摆的：

| 概念 | 存在哪 | 金额 |
|---|---|---|
| 花销 | `expenses`（kind=0） | 正 |
| 收入 | `expenses`（kind=1） | 正 |
| 退款/返现 | `adjustments` **子表** | 正，挂在原账上 |

它有三个毛病，而且都不是小毛病：

**① 表名在撒谎。** 一张叫 `expenses` 的表里装着收入。

**② 退款需要一整套零件。** 子表 + `refundedCnyCents` 缓存列 + 「缓存和明细必须在一个事务里改」的约束。四月份任何一条聚合 SQL 忘了 `- refundedCnyCents`，数字就悄悄错了。

**③ 最要命的是 `kind` 过滤。** 上一次批量加 `AND e.kind = 0` 时漏了一条，结果分析页总额 `5,334.89`、分类占比合计 `334.89`，差了整整 5000 —— 而且不报错、不崩溃，页面看起来完全正常。

第三条不是手滑，是**结构问题**：只要「两个语义不同的东西」住在同一张表里，每个查询都欠一次过滤，而漏一次不会有任何提示。

## 二、新的划分

| | 账本 A：花销 | 账本 B：收入 |
|---|---|---|
| 表 | `expenses` | `incomes` |
| 装什么 | 花销（正）、退款/返现（**负**） | 挣钱、存款 |
| 分类 | kind=0 | kind=1 |
| 回答的问题 | 这个区间净流出多少 | 这个区间挣了多少 |

**退款不再有子表、不再有缓存列。** 它就是一条金额为负的账，落在「退款」或「返现」分类里。

```sql
-- 花了 100，退了 20，两条独立的行
INSERT INTO expenses (amountMinor, ...) VALUES ( 10000, ...);  -- 花销
INSERT INTO expenses (amountMinor, ...) VALUES ( -2000, ...);  -- 退款
```

好处是**所有聚合天然正确**：`SUM(amountMinor)` 自己就会减。不用 JOIN、不用缓存、不用事务约束。桌面组件、日均、趋势、合计，一处都不用改。

## 三、负额的坑：年月日合计可能是负数

这是这次改动唯一真正需要动脑的地方。用户的原话：

> 但是有个bug，就是年月日的总花销可能有负数，这个要处理一下，我没想好，你思考下怎么办

**根源不是「负额」，是把「净额」和「支出」当成了同一个数。**

拆成三个数，负号就永远落在它该落的地方：

```
支出合计 = SUM(正数行)   ≥ 0     ← 大字显示这个
退款合计 = SUM(负数行)   ≤ 0     ← 显示「退款 CNY -20.00」
净额     = 两者相加      可正可负  ← 显示「净 CNY 264.89」
```

只退不花的月份：**支出 CNY 0.00 · 退款 CNY -20.00 · 净 CNY -20.00**。
「花了 −20 元」这句话永远不会出现在界面上，因为「支出」这个数按定义就 ≥ 0。

配套四条规则：

| 位置 | 口径 | 理由 |
|---|---|---|
| 日均 | 支出合计 ÷ 已过天数 | 恒 ≥ 0，不出现「日均 −0.67 元」 |
| 分类占比 | 只用**正数行** | 分母恒 > 0；负的扇区画不出来 |
| 趋势折线 | **净额** | 允许跌破 0 —— 那天净退了钱，线朝下就是对的 |
| 空状态 | 区间无支出 → 不画环图 | 「本月没有支出，只有 N 笔退款」比画个空环诚实 |

## 四、迁移 4 → 5

SQLite 的 `ALTER TABLE DROP COLUMN` 要 3.35+（Android 14 起），本项目 minSdk 26 —— 所以**只能重建表**：

```
① categories 加「退款」「返现」两个分类
② 建 incomes 表，把 kind=1 的行搬过去
③ 建 expenses_new，把 kind=0 的行搬过去
④ adjustments 里的每一笔，变成 expenses_new 里的一条负数行
⑤ DROP adjustments → DROP expenses → RENAME expenses_new
⑥ 重建三个索引
```

要命的细节：**建表语句必须和 Room 生成的逐字一致**，连 `ON UPDATE NO ACTION ON DELETE CASCADE` 这种不写也不会报错的部分都得有，否则迁移完 Room 校验结构时直接抛异常 —— 一开 app 就崩。

退款搬过去时，汇率和币种要**沿用原账的快照**（不是当前汇率），否则一笔 100 港币的消费退了 20，净额算出来不是 80 港币的等值人民币。

### 实测

| | 升级前 (v4) | 升级后 (v5) |
|---|---|---|
| `user_version` | 4 | **5** |
| `expenses` | 9 笔，合计 87303 分 | **9 笔，合计 87303 分** |
| `incomes` | — | **1 笔，合计 500000 分** |
| `adjustments` 表 | 存在 | **已删除** |
| `kind` 列 | 存在 | **已删除** |
| `refundedCnyCents` 列 | 存在 | **已删除** |
| 分类数 | 12 | **14**（+退款、+返现） |
| 崩溃 | — | **0** |

一分钱都没差。

## 五、记账页：三段切换

`[− 支出] [↩ 退款] [+ 收入]`

- 支出 → `expenses`，金额取正
- 退款 → `expenses`，金额**取负**，分类默认选中「退款」
- 收入 → `incomes`，金额取正，分类切到收入体系

**为什么要预选「退款」分类**：退款/返现排在芯片列表最右边，屏幕上根本看不见。不预选的话用户会以为没得选，然后卡在那里。同时把芯片行自动滚到底，让选中项真的出现在视野里。

同理，**退款不再需要「点原账 → 弹窗」这条路**。它就是一个普通的记账动作，日期自己选，因此天然满足「退款可选时间」。

## 六、回顾页：两个账本

顶部一对芯片 `[花销] [收入]`。两者的列表长得像，但**不共用模型** —— 收入没有退款、没有净额、不进分类占比，硬套一个模型只会到处写 `if`。

花销账本的汇总卡：

```
支出合计
CNY 884.89                      10 笔
退款 CNY -20.00 · 净 CNY 864.89
```

退款行在列表里是紫色的，金额带负号 —— 一眼分得出来。

## 七、备份升 v3

```
formatVersion: 3
data: { categories, currencies, expenses, incomes }
```

- `expenses` 里的 `kind` 字段删掉了；退款就是负数行，符号本身携带语义
- 新增 `incomes` 块
- **v2 文件导入时自动把 kind=1 的行搬进 incomes** —— 用户手机里的旧备份永远不会变，必须一直读得懂

这也是上一轮那个缺口的补丁：之前 `formatVersion 2` 导出**不带退款**，导出再导入退款会凭空消失、净额变回毛额。现在退款是普通行，跟着 `expenses` 一起走，不会再丢。

## 九、这次学到的

**① 一个语义一个家。** 收入住在 `expenses` 里的时候，每个查询都欠一次 `kind = 0`，而漏一次不报错。换个表，这类 bug 从结构上不可能发生 —— 比「记得写过滤条件」可靠一万倍。

**② 冗余是有价格的，而且账单在别处。** 缓存列 `refundedCnyCents` 让查询变短了，代价是「两份数据」和「必须在一个事务里改」。省下的那点 JOIN，最后要用一次迁移和一堆约束还回去。

**③ 「这个数可能是负数」不是显示问题，是口径问题。** 第一反应会想去 clamp、去取绝对值、去改显示。真正的解法是问「这个负数在语义上属于哪个数」—— 它属于「退款合计」，不属于「支出」。

**④ 表重建是 SQLite 的日常。** `DROP COLUMN` 在老安卓上没有，改一个列就得整表重建：建新表 → 搬数据 → 删旧表 → 改名 → 重建索引。而且建表语句必须和 Room 的期望逐字一致，差一个 `ON DELETE CASCADE` 就开不了 app。
